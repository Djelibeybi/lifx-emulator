product-ID literal anywhere in Python. The ceiling is data (`specs.yml`); the rule is generic.

product-ID comparison anywhere in Python. The Tile rejection is arithmetic: the ceiling from
`specs.yml` (3.50) sits below the Thread floor (4.200), so a Thread Tile cannot resolve.

**`factories/firmware_config.py`** — per D-05, the Thread default and the Thread floor are one
constant: add a class constant `VERSION_THREAD = (4, 200)` beside `VERSION_EXTENDED` and
`VERSION_LEGACY`, with an inline comment naming it as the Thread minimum and default.

Add a fourth parameter to `get_firmware_version()`, after `override`, typed
**`connectivity: Connectivity | None = None`** — the narrow enum type, NOT `Connectivity | str | None`.
Addresses review concern (Codex MEDIUM): the wider annotation would have declared a contract this
method does not honour, because the body compares directly against `Connectivity.THREAD` and an
unrecognised string such as `"bluetooth"` or a mis-cased `"Thread"` would silently take the WiFi
branch. String coercion is the builder's job and happens once, in `_resolve_connectivity()`, before
this method is reached; Pyright standard now flags any caller that tries to pass a raw string.
D-03's `Connectivity | str | None` remains the signature of the public factories and
`DeviceBuilder.with_connectivity()` — this narrowing applies only to the internal resolver. Four
non-`self` parameters keeps it inside the documented `max-args = 5` budget.

Restructure the body into one resolution followed by two validations, **in this order**:
resolution order is `override` first, then `Connectivity.THREAD` yielding `VERSION_THREAD`, then the
product default from `get_default_firmware_version(product_id)`, then `extended_multizone is False`
yielding `VERSION_LEGACY`, else `VERSION_EXTENDED`.

Validation 1 (floor) — runs FIRST: when connectivity is Thread and the resolved tuple compares less
than `VERSION_THREAD`, raise `ValueError` with an f-string message naming the required minimum and
the resolved value. Ordering is load-bearing, not incidental:
`get_firmware_version(product_id=55, connectivity=Connectivity.THREAD, override=(3, 40))` must fail
on the Thread floor, not pass the ceiling check and yield an invalid Thread version. Addresses review
concern: Antigravity MEDIUM / suggestion, floor-before-ceiling precedence.

`product_id` is not `None`, call the module-level `get_max_firmware_version(product_id)`; when it
returns a tuple and the resolved value compares greater, raise `ValueError` with an f-string message

device from its product's terminal firmware — `create_device(55, firmware_version=(4, 200))` must
raise naming `(3, 50)`, exactly as the unrequested-default case does. When the rejection was caused
by an unrequested Thread default — connectivity is Thread and `override` is `None` — append a clause
to that message stating that the Thread default cannot be reduced to fit, so the single message names
both the floor that forced the value and the ceiling that rejected it (D-06's "naming both"). Tuple
